Fund Narrative Intelligence System

基金重仓叙事可持续性分析系统：需求定义与架构边界

V1 Scope Narrative-Centric Evidence-Based Report-First Monolith-First

1.系统定位不是预测涨跌，而是做基金重仓叙事体检

系统服务于有经验的个人投资者或研究者。用户输入基金代码，系统读取基金前十大重仓股，识别基金实际押注的市场叙事，并评估这些叙事当前是否仍然成立。

核心定位：这是一个 Narrative Intelligence System，而不是买卖建议系统、短线预测系统或自动投顾系统。

系统回答的问题不是“这只基金明天涨不涨”，而是：

  • 这只基金真正押注的是什么市场叙事？
  • 这些叙事是否还有资金、业绩和市场语言支撑？
  • 叙事处于启动、强化、拥挤、分歧还是衰退阶段？
  • 支持证据和风险证据分别是什么？

2.系统核心对象是 Narrative，而不是基金本身

基金是入口对象，重仓股集合是分析载体，Narrative 是最终分析目标。

Fund → Holdings → Stock → Narrative → Narrative State → Report

这意味着系统不是简单的基金分析器，而是通过基金持仓暴露来识别市场叙事。

对象系统角色
Fund用户输入入口
Holdings分析载体，保留基金到股票的映射
StockNarrative 归因的最小可解释单元
Narrative核心 domain object
Signal影响 Narrative State 的标准化市场脉冲
Evidence支撑 Signal 和 Narrative 判断的原始依据

3.Narrative 采用固定 Taxonomy 与动态 Narrative 双层模型

固定 taxonomy 用于稳定分类、长期比较和数据建模；动态 Narrative 用于表达市场正在交易的真实语言。

Canonical Taxonomy
  ↓
Major Narrative
  ↓
Sub Narrative

示例：

AI
  └── AI Infrastructure
        └── AI Power Demand

动态 Narrative 不能由 LLM 凭空发明，必须来自市场语言，包括新闻、研报、财报电话会、公司公告、ETF 主题、社交媒体和龙头公司表述。

4.Narrative Registry 是慢变化的核心基础设施

Dynamic Narrative 必须实体化，进入 Narrative Registry。系统不能每次查询时临时生成 Narrative，否则无法保持历史连续性、生命周期跟踪和可回放能力。

{
  "narrative_id": "N_AI_POWER_001",
  "canonical_taxonomy": "AI",
  "name": "AI Power Demand",
  "parent_id": "N_AI_INFRA_001",
  "level": 2,
  "status": "active",
  "aliases": ["AI electricity demand", "datacenter power demand"],
  "related_terms": ["data center", "power grid", "nuclear", "cooling"],
  "human_review_status": "approved",
  "first_seen_at": "2024-09-01",
  "last_updated_at": "2026-05-13"
}

V1 支持层级结构，但避免进入知识图谱泥潭。只做 tree-like hierarchy、alias matching、human-approved registry，不做 Graph DB、RDF、ontology 或复杂多跳推理。

5.系统采用 Slow Intelligence + Fast Query 架构

Narrative 不是分钟级对象。系统不应该每次用户查询时重新理解市场，而应该维护慢变化的 intelligence layer，再用前台快速查询生成报告。

模块建议频率说明
Narrative DiscoveryWeekly扫描市场语言，生成 candidate narratives
Narrative RegistryWeekly / Human Review确认、合并、拒绝候选 Narrative
Stock → Narrative MappingWeekly慢变化映射，避免每日漂移
Narrative State SignalsDaily / Event-driven刷新资金、估值、风险和热度信号
Fund AnalysisOn-demand用户输入基金代码后生成报告

重大事件可以触发 deeper reassessment，例如财报、政策变化、龙头暴跌、ETF 异常流入或关键词爆发。

6.Stock → Narrative Mapping 采用规则候选 + LLM 消歧

系统采用 bottom-up narrative inference。先将每只股票映射到多个 Narrative，再根据基金持仓权重聚合出基金的主 Narrative 和次级 Narrative。

Stock → Multi-level Weighted Narrative Mapping
Fund → Aggregated Narrative Exposure

Mapping 必须支持多层级、多权重和置信度。

[
  {
    "stock": "VST",
    "narrative": "AI Infrastructure",
    "level": 2,
    "weight": 0.7,
    "confidence": 0.78
  },
  {
    "stock": "VST",
    "narrative": "AI Power Demand",
    "level": 3,
    "weight": 0.9,
    "confidence": 0.84
  }
]

规则负责生成候选，LLM 负责消歧、权重判断和解释。不能完全依赖 LLM，也不能完全依赖硬编码标签。

7.Narrative Sustainability 由五个维度组成

维度含义
Earnings Validation题材是否已经转化成收入、利润、毛利率、ROE 或订单支撑
Capital Reinforcement资金是否继续强化该方向，包括成交额、ETF 流入、机构资金和换手率
Valuation Pressure叙事是否已被过度定价，包括估值分位和相对行业估值
Narrative Momentum市场语言是否仍在强化，包括新闻、研报、公告和龙头公司表述
Counter Evidence Risk反证是否增加，包括业绩不及预期、订单取消、政策收紧、库存上升和技术路线变化

系统同时输出连续信号和离散阶段。连续信号用于计算、排序和趋势；离散阶段用于人类理解。

Emerging → Strengthening → Expanding → Crowded → Diverging → Weakening → Dead

Crowded 不等于看空。真正危险的是 Crowded + Counter Evidence Increasing。

8.Evidence 是一等公民，不能只输出 LLM 结论

系统必须保留 raw evidence 和 normalized signal 双层结构。

Raw Market Information
  ↓
Evidence Extraction
  ↓
Normalized Signal
  ↓
Narrative Interpretation
  ↓
Narrative State

Evidence 用于解释、调试、人工审查和未来 replay。Signal 用于评分、聚合和趋势分析。

{
  "evidence_id": "EV_001",
  "narrative_id": "N_AI_POWER",
  "type": "earnings",
  "source": "earnings_call",
  "title": "Company raised AI infrastructure guidance",
  "summary": "Management raised guidance due to AI datacenter demand.",
  "sentiment": "positive",
  "confidence": 0.82,
  "event_date": "2026-05-13"
}

9.Signal Service 维护标准化市场脉冲，而不是 Narrative-specific 结论

Signal 是 market primitive，不应该包含 AI、GLP-1、核电等业务语义。Narrative Service 负责在上下文中解释 Signal。

Signal Type说明
revenue_growth_up收入增长强化
guidance_raise公司上调指引
capex_increase资本开支增加
institutional_inflow机构资金流入
valuation_extreme估值处于高风险区
demand_slowdown需求放缓
margin_pressure利润率承压
regulatory_risk监管风险上升

Signal Vocabulary 采用 governed evolution：Core Signals 稳定，Derived Signals 可扩展，Experimental Signals 进入候选队列，由人类确认后晋升。

10.Signal 不是永久事实，而是有衰减的时间对象

Signal 影响力必须随时间衰减。旧 signal 不能永久污染 Narrative State。

{
  "signal_id": "SIG_001",
  "signal_type": "guidance_raise",
  "strength": 0.82,
  "confidence": 0.76,
  "created_at": "2026-05-13",
  "half_life_days": 45,
  "decay_function": "exponential"
}

系统不应该直接删除旧 signal，而应该让 influence decay。Narrative 变弱不一定因为坏消息出现，也可能因为正面强化证据停止出现。

11.Signal 分为 Signal Event 与 Signal State

单条事件不是 Narrative 状态。Narrative 状态来自 signal over time 的积累、衰减和趋势。

Signal Event

原子事件。例如一次 guidance raise、一条新闻、一个公告、一次资金流入。

Signal State

聚合后的状态。例如 7d / 30d / 90d 的 current_strength、trend、momentum。

V1 只需要 event → rolling aggregation → signal state，不需要 Kafka、streaming infra 或实时复杂事件处理。

12.V1 采用 Monolith-First，但模块边界要清晰

V1 不拆微服务。逻辑上分服务，部署上保持单体，避免过早分布式复杂度。

src/
  main.py
  orchestrator.py
  models/
  modules/
    narrative_registry/
    signal_service/
    evidence_service/
    fund_analysis/
    report_writer/
  providers/
  outputs/
  docs/

模块边界：

  • Narrative Registry Module：维护已确认 Narrative、层级、别名、状态。
  • Signal Module：维护 signal vocabulary、signal events、signal states、decay。
  • Evidence Module：保存 raw evidence 与 source link。
  • Fund Analysis Module：基金持仓、股票映射、Narrative 聚合。
  • Report Module：生成 Markdown / HTML 报告。

13.V1 最小闭环必须严格收敛

V1 的目标是证明“基金 → 重仓股 → Narrative → State → Evidence Report”这条链路成立，不是一步到位构建完整市场 intelligence platform。

基金代码
  ↓
获取前十大重仓股
  ↓
股票标签与 Narrative Mapping
  ↓
Fund Narrative Aggregation
  ↓
读取当前 Signal State
  ↓
计算 Narrative State
  ↓
生成 Markdown / HTML Report

V1 必须做

  • 输入基金代码。
  • 获取或 mock 前十大重仓股。
  • 保留 Fund → Stock 映射。
  • 将股票映射到多层级 Narrative。
  • 聚合基金主 Narrative 和次级 Narrative。
  • 基于五维评分生成 Narrative State。
  • 输出支持证据和风险证据。
  • 生成报告，但不给买卖建议。

V1 暂不做

  • 自动发现所有新 Narrative。
  • 自动治理 Signal Vocabulary。
  • 完整历史回放。
  • 复杂知识图谱。
  • 实时预警。
  • 前端 workspace。
  • 买入 / 卖出信号。

14.Deferred Capability 必须记录，而不是遗忘

不做不是没想到，而是明确延后。项目需要保留 architecture memory。

docs/

    ADR-002-signal-decay-design.md

每个 deferred capability 至少记录 Capability、Why Deferred、Current Limitation、Future Design Direction、Dependencies、Risk If Ignored。

15.Human Review 是治理核心

系统可以让 AI propose，但不能让 AI 直接改变核心 registry。

LLM / Rules propose
  ↓
Candidate Narrative / Candidate Signal
  ↓
Similarity Check / Frequency Analysis
  ↓
Human Review
  ↓
Approve / Merge / Reject
  ↓
Registry Update

需要治理的对象包括：

  • Candidate Narrative。
  • Derived Signal。
  • Experimental Signal。
  • 同义 Narrative 合并。
  • Narrative 生命周期状态变化。

16.系统必须表达不确定性和 Narrative 冲突

系统输出的是当前市场状态解释，不是绝对真理。每个结论都应该带 confidence、evidence density、freshness 和 contradiction risk。

{
  "stage": "expanding",
  "confidence": 0.68,
  "evidence_density": "medium",
  "counter_signal_risk": "rising"
}

系统必须允许同一只股票或基金暴露在多个冲突 Narrative 下。例如一只股票同时具有 growth narrative、valuation bubble narrative 和 demand slowdown narrative。

Narrative 也不应天然 bullish，应支持：

bullish | bearish | mixed

17.V1 输出采用 Report-First，而不是 Workspace-First

V1 只输出结构化报告，不做复杂 UI 工作台。但内部对象必须 workspace-ready。

报告应包含：

  • 基金基本信息。
  • 前十大重仓股。
  • 主 Narrative 和次级 Narrative。
  • Narrative 权重与置信度。
  • 五维评分。
  • 生命周期阶段。
  • Top supporting evidence。
  • Top risk evidence。
  • 明确声明：不构成投资建议。

报告不能信息过载。每份报告优先展示 1 个 primary narrative、2–3 个 secondary narratives、关键支持证据和关键风险证据。

18.V1 成功标准是验证架构，而不是跑赢市场

成功标准判断方式
Narrative 抽象成立用户看到报告后认可该基金真正押注的 Narrative
Narrative State 像真人研究解释合理、证据连贯、信号一致
Evidence 可追溯用户能看到判断依据，而不是只看到结论
Multi-Narrative Aggregation 合理能区分 AI Infrastructure、AI Application、AI Power Demand 等细分叙事
架构支持未来演化未来加入 replay、alert、workspace、auto discovery 时不用推倒重来
V1 目标：Validate the Narrative Intelligence Architecture，不是 Beat the Market。

20.核心结论

这套系统的核心不是 Agent orchestration，也不是财经新闻摘要，而是把市场叙事结构化为可维护、可解释、可演化的 domain object。

V1 应该只做一个收敛闭环：

Fund → Holdings → Stock Mapping → Narrative Aggregation → Signal-backed Narrative State → Evidence Report

只要这个闭环成立，系统就具备继续扩展到 Narrative Discovery、Signal Governance、Historical Replay、Alerting 和 Workspace 的基础。
